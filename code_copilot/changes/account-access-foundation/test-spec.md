执行时间 2026-09-19（第 5 轮，fix 轮次 4 之后；用户指定范围为 Web Locks 多标签与浏览器链路，编排同时把其余用例一并重跑。fix 轮次 4 移除了无 Web Locks 时的租约降级，故本轮重点复核 Web Locks 路径未回归、持久存储无任何协调元数据）；后端 Go 1.26.6（toolchain 自动切换）、Node 24.15、PostgreSQL 17.11（临时容器 `pgvector/pgvector:pg17`）、真实 nginx 反代容器、1 vCPU/512 MiB 受限容器、真实 Chrome for Testing 148.0.7778.96。所有用例都在真实进程与真实数据库上执行，未使用 Mock 顶替业务验证。

第 4 轮编排 24 个用例分组再次全部通过（P0-13 12/12 与 2/2，浏览器 16/16）。轮次 3 记录的三条 must-fix（`R1-F1`、`R1-F2`、`R1-F3`）与轮次 3 新发现的 `T3-F1` 均已在轮次 3 的 fix 中修复，本轮复核通过。

### 本轮增补：经 nginx 的浏览器链路

既有浏览器用例走 Vite 开发代理（`vite.config.ts` 把 `/api` 代理到 `:8080`），**不经过 nginx**，而 fix 轮次 3 改动的正是 `web/nginx.conf`。因此本轮另跑了一条 Compose 形态的浏览器链路（`t_browser_nginx.sh`）：用 compose 声明的子网建网络，把 api 与 nginx 都放进容器、nginx 固定到 `172.30.0.10` 并挂载仓库自带的 `web/nginx.conf`、以刚构建的 `web/dist` 作为站点根，然后对 `http://localhost:5173` 重跑同一套浏览器用例。

结果 **16/16 通过**：注册校验与跳转、登录失败与重试、账户页、令牌不落持久存储、重载由刷新 Cookie 恢复、改昵称、双标签共享登录态、并发重载后都保持登录、跨标签退出广播、退出后重定向、缺 CSRF 头刷新 403、匿名列表与文章详情。说明 nginx 改为 `$remote_addr` 覆盖转发头后，浏览器可见链路没有回归。

### 本轮修掉的两处 harness 缺陷（非产品问题）

- `t_browser.mjs` 的「租约只含元数据」断言在租约移除后恒真，已改为断言持久存储全程为空（`{"local":{},"session":{}}`）——否则它是一份假证据。
- 同一脚本的「匿名可打开文章详情」在文章链接出现前就判定，把「列表仍在加载」误判成「没有文章」；第一次失败即由此产生（当时库中文章为 `published` 且存在）。已改为轮询等待链接出现。两次失败都属 harness 自身，不是实现回归。

### T3-F1 定向复核

`t_compose_net.sh` 在本轮 9/9 通过：可信代理范围是反代自身的 `172.30.0.10/32`、反代容器地址与之一致、网关不在可信范围内、启动日志记录实际生效网段；经 nginx 反代时无转发头解析为网关、**伪造的 `X-Forwarded-For` 仍解析为网关**、两个伪造值落到**同一 IP 维度键**；**绕过反代直连 API 发布端口**时，无转发头与伪造转发头都解析为 TCP 对端。fix 轮次 3 的修复在测试阶段独立复核成立。

轮次 3 为 fix 轮次 2 的三条 must-fix 增补的定向验证（保留备查）：

- **R1-F1 定向验证（`t_compose_net.sh` / `t_compose_net.mjs`）**：从 `docker compose config` 取出 `networks.default.ipam.config[0].subnet` 与 `services.velis-api.environment.VELIS_AUTH_TRUSTED_PROXY_CIDRS`，断言两者一致（均为 `172.30.0.0/24`）；再用同一子网建真实网络，把 api 与 nginx 都放进容器、挂载仓库自带的 `web/nginx.conf`，观察来源 IP 判定。结果：子网一致、反代容器地址落在可信网段内、启动日志记录实际生效网段三项通过；并发现一条新缺陷（见下）。
- **R1-F2 定向验证**：真实 PostgreSQL 上跑集成测试正例（14 个用例全通过），再跑负例——`path` 为 `velis_test` 但查询串带 `dbname=velis` 的 DSN 被拦下并报出「实际连接目标是 "velis"」，事后核对目标库表数仍为 0，证明未迁移也未清表。
- **R1-F3 定向验证**：前端用例覆盖「租约到期时间按写入时刻起算」与「等待期间有人接管时重新等待」；两例在修复前的实现下均断言失败。**该机制已在 fix 轮次 4 随 R2-F1 一并移除，本节仅作历史记录。**

## 未覆盖与 Deferred

- **本轮未覆盖**：Safari/Firefox 与生产同源反代形态的浏览器行为（只在 Chrome for Testing 148 + Vite 开发代理下验证）；无 Web Locks 时的刷新行为未在真实浏览器触发（该分支的租约降级已在 fix 轮次 4 移除）；真实抓取链路（抓取器按设计拒绝 loopback/私网目标，本机无法构造合规抓取源，文章读取改用直接入库数据验证）；多主机部署与持续压测（资源与多实例结论来自单机容器）；`取消请求后未完成计算仍占额度` 未在 HTTP 层构造（由适配器单测覆盖）。
- **已知限制（非本轮失败）**：无 `/metrics` 端点；无改密/找回/注销；被登出的其他标签页不会自动跳转登录页（令牌已失效，导航时由路由守卫拒绝）。
- **Compose 本地拓扑无法按客户端隔离（实测，非缺陷但需记录）**：nginx 在容器里、端口以 `-p 5173:8080` 发布时，宿主上的浏览器到达 nginx 的 `$remote_addr` 是 Docker 网桥网关 `172.30.0.1`，真实客户端地址在发布端口处已经丢失。实测「无转发头」的登录失败被解析成 `172.30.0.1`，因此本机所有浏览器共用同一个 IP 维度键。远程客户端不受此影响（其源地址经 DNAT 保留，落在可信网段之外，会成为最右的不可信跳点），但本机没有第二台主机可复现该路径，属推理而非实测。spec §4.2 与 P0-13 的「反代拓扑下按真实客户端隔离」在生产拓扑成立，在 Compose 本机拓扑不成立；既有 P0-13 用例是通过测试自带的覆盖式转发头模拟多个客户端的，不等于本地拓扑下的真实隔离。
- **规格内部张力（供 Review 判定）**：spec §10 第一条允许记录"确认身份后的用户 ID/会话 ID"，同节末句又禁止把"用户、会话"写成字段值；实现按第一条记录 `user_id`/`session_id`，若后续接入 Prometheus，这两个高基数字段不可作为标签。
- 真实 PostgreSQL 必须使用专用 `_test` 库并应用 `000003`，执行会清表；未设置测试 URL 的跳过不能算通过。Playwright E2E、Prometheus 指标与 `/metrics` 端点不在本 change 的验证范围。生产部署、外部身份服务、复杂前端和后续 Agent 能力同样不在范围内。
