### R1-F1 Compose 可信代理默认值与真实网络不符，IP 维度限流静默退化

- **位置**：`compose.yaml:83`（默认值）、`compose.yaml:80-82`（注释）、`backend/configs/config.example.yaml:41-43`、`.env.example:18-19`、`backend/internal/interfaces/http/hertz/middleware/client_ip.go:21-23`、`backend/internal/bootstrap/api.go:61`、`web/nginx.conf:7-12`
- **触发条件**：以 Compose 部署并开启认证，且未显式覆盖 `VELIS_AUTH_TRUSTED_PROXY_CIDRS`。

- **证据**：
  - 实测 `docker network inspect velis_default --format '{{json .IPAM.Config}}'` → `[{"Subnet":"172.23.0.0/16","Gateway":"172.23.0.1"}]`；`172.18.0.0/16` 属于**无关项目** `dev-ops_my-network`。
  - `compose.yaml` 全文无 `networks:` / `ipam`，子网由 Docker 动态分配，硬编码任何猜测值都不可能稳定正确。

### R1-F3 无 Web Locks 时租约写入即过期且等待方不复检，跨标签串行化失效

- **位置**：`web/src/features/auth/session.ts:178-193`（关键行 `:180`、`:182`、`:187`）
- **触发条件**：浏览器无 Web Locks（`browser.ts:33-40` 返回 null）→ 走租约降级路径；同时 ≥2 个标签正在刷新，且先持有租约者刷新失败、被关闭，或在租约被接管后的一个刷新窗口内有新标签开始刷新。
- **影响**：租约不再保证「同一时刻只有一个刷新者」，两个标签用同一枚单次刷新 Cookie 并发调用 `POST /auth/refresh` → 服务端按 `spec.md:39`「旧令牌再次出现时撤销当前会话」处理 → 会话被撤销，用户被强制登出。这正是该机制（`spec.md:96`、AC-10、P1-02）存在的目的。
- **证据**：
  ```ts
  180    const startedAt = now()
  181    if (existing && existing.owner !== tabId && existing.expiresAt > startedAt) {
  182      const peer = await waitForPeer(existing.expiresAt - startedAt)   // 最长阻塞一整个剩余租约
  ...
  187    lease.write({ owner: tabId, expiresAt: startedAt + leaseTtl })   // 用的是等待前的 startedAt
  ```
  两个独立机制（均已核实）：
  1. **写入即过期**：等待时长 = `existing.expiresAt - startedAt`，超时返回时 `now() ≈ existing.expiresAt`；若被等待的租约较新，则 `existing.expiresAt ≈ startedAt + leaseTtl`，`:187` 写下的到期时间恰好落在当下 —— 新租约写入瞬间即已到期。此刻到达的标签（`:181` 判定为假）不会等待，直接并发刷新。
  2. **等待后不复检**（裁决阶段补充）：`:182` 之后没有重新 `lease.read()`。所有同时在等待的标签会在同一刻一起超时、一起 `write` 并一起 `callRefresh()`，即使有人刚写下有效租约也不会被观察到。
- **建议方向**：`lease.write` 用写入时刻的 `now()` 计算到期时间；并在 `waitForPeer` 返回后重新 `lease.read()`，已有他人有效租约则继续等待而非直接刷新。
- **可达性与限制**：真实浏览器路径**未验证** —— `test-spec.md:68` 已自述「无 Web Locks 时的租约降级分支未在真实浏览器触发（仅纯 TS 单测）」，P1-02 的多标签结论是在支持 Web Locks 的 Chrome 上取得的。若首刷新者成功且 BroadcastChannel 可用，其他标签会收到令牌而不会超时，故触发依赖首刷新者失败 / 标签被关 / 接管窗口内出现新标签。后果是会话被撤销（需重新登录），不涉及越权或数据损坏；结论来自代码路径推演。

## 裁决问题

1. **spec §10 日志基数张力 —— 实现可接受，建议改规格措辞。** `spec.md:196`（第一条）明确允许「确认身份后的用户 ID/会话 ID」；`spec.md:197`（末条）在谈论指标载体时说「禁止把用户、会话、IP、用户名或 HMAC 查找键写成字段值」。同一节对同一对象给出相反指令，属规格内部张力，不能据此判实现违约：特别规定优先于一般规定，且第一条是唯一对日志内容作出肯定授权的句子。实现（`handler/account.go:178-189`）严格按第一条记录并对零值跳过（失败路径不写未确认身份的 ID），与末句「确认身份后」的限定一致。三方判定一致，**实现可接受**；C 补充的「接入 Prometheus 时这两个字段不可作标签」与 §10 末句同向。属规格澄清项，不是 finding。
2. **密码「等于用户名」判定 —— 实现符合规格字面，不构成 finding。** `spec.md:26` 的「比较时仅对 ASCII 字母忽略大小写」显式限定在**密码表比较**上，第三个分句「密码与规范化用户名完全相同也拒绝」未沿用该限定；而 `spec.md:15` 规定用户名已按 ASCII 小写规范化。因此 `domain/account/password.go:62` 的精确比较是对规格字面的正确实现。补充量化事实：密码下限 8 位、用户名上限 32 位，故长度 ≤7 的用户名根本不能成为密码。**规格需澄清**：若意图是拒绝大小写变体，须在 §2.2 写明「忽略 ASCII 大小写后与规范化用户名相同也拒绝」。
3. **候选 12（Compose 未透传认证变量）→ important**（采纳 C，不采纳 A）。判据是「按正确文档操作却得到错误结果」：README:150-160 与 `.env.example:10-19` 都按 Compose 消费的口径写，实际不生效。未升 must-fix 的理由：失败响亮（认证路由 404），不产生静默安全误判。**注意与 R1-F1 的相互影响**：补齐透传后，错误默认可信代理网段的危害面会随之扩大。
4. **候选 11（配置示例两套取值）→ suggestion**（采纳 C，不采纳 A）。示例是「认证关闭 + 带注释骨架」形态，照抄不会启动失败、更不会静默产生错误安全姿态（一旦开启 `enabled` 而 `allowed_origin` 为空会响亮失败，P1-05 已覆盖 11 项非法配置启动失败）；spec §4.1 的「必须同时给出两套取值」在 README:158-162 已用文字满足。
