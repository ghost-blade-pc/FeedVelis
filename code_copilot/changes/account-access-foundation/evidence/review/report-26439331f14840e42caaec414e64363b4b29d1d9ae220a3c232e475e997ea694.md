## 分歧的裁断

方向一与方向二在「无 Web Locks 时租约能否保证同一时刻只有一个刷新者」上结论相反，且各自只报了其中一部分机制。裁决方实测后判定：**三条机制同属一个缺陷，且两个方向都低估了对方那条**。

- 方向一报的 **(a) 接管发生在持有者仍在飞行时**需要刷新挂起超过 10 秒；
- 方向二报的 **(b) 两标签同时读到空租约****不需要任何异常条件**——裁决方在真实 Chromium 148（关掉 `navigator.locks`）并发加载两个标签页，干净批次 **20 次里 4 次**出现两个刷新请求携带同一枚 Cookie，同一毫秒到达（另一批 8 次里 1 次）；对照组（Web Locks 可用）每次都只有 1 个刷新请求。

裁决方据此把两者合并为**一个** must-fix `R2-F1`，而不是拆成两条。

## must-fix

### R2-F1 无 Web Locks 的租约降级仍会在同一枚单次刷新 Cookie 上产生并发刷新

- **位置**：`web/src/features/auth/session.ts:178-205`（`refreshWithLease`；关键行 `:182` 读租约、`:187-189` 到期即 `break`、`:190` 等待、`:199` 写租约、`:201` 刷新、`:202-204` `finally` 无条件清租约）；`web/src/features/auth/browser.ts:88-93`（`clear()` 就是 `storage.removeItem`，不看 owner）；`web/src/api/client.ts:32-54`（`request()` 只透传 `signal`，无超时）与 `session.ts:234`（`options.transport.refresh(csrf)` 不传 signal）；`web/src/main.ts:10` 与 `web/src/router/index.ts:32`（每个标签页加载即 `restore()`）。服务端后果：`backend/internal/infrastructure/persistence/postgres/session_repository.go:140-147`。
- **触发条件**：
  - **(b)** 两个标签页同时启动刷新（同一秒内），都读到「无租约」→ 各自写租约并刷新。**不需要任何异常条件**，就是「同时打开/恢复两个标签页」。
  - **(a)** 持有者刷新挂起超过租约 TTL（10 秒）→ 等待者到期接管 → 两次并发刷新。
  - **(c)** (a)/(b) 之后，先完成的一方在 `finally` 里清掉**不是自己写的**租约（`clear()` 无归属语义），成为放大器。
- **影响**：两次请求携带同一枚单次轮换 Cookie 到达服务端 → `session_repository.go:140-147` 按 `consumed_at != nil` 撤销整个会话（`revoke_reason='replay'`）→ 所有标签页被强制登出。即 `spec.md:39`「旧令牌再次出现时撤销当前会话」被客户端自己触发，而这正是 §2.3「前端协调并发刷新」、§4.3 与 AC-10 的租约降级存在的目的。
- **证据**（裁决方与方向一各自实测，非转述）：
  1. 真实构建产物 + 真实 Chromium 148，`navigator.locks` 置空走真实降级分支，mock 后端记录每个刷新请求携带的 Cookie：干净批次 20 次命中 4 次，命中时两个请求同一毫秒到达；对照组（Web Locks 可用）每次只 1 个请求。
  2. 仓库原样 `session.ts`（tsc 逐字节转译，sha256 与仓库一致）+ 真实 10 秒 TTL 实测接管时间线：`10139:tab-b:refresh-start:token-x` —— 恰好 TTL 到期时接管，两个在飞。
  3. 跨标签 `localStorage` 可见性对照：读取方让出事件循环时 12/12 命中、滞后 0–1ms；处于同步块内时 0/12 命中。而 `main.ts:10` 的 `lease.read()` 正在模块求值的同步块内——两标签同时加载时同步块重叠，故 (b) 可达。
  4. (c) 为代码事实（`clear()` 无条件 `removeItem`），裁决方按代码核实、未单独稳定复现，判定为放大器而非独立触发路径。
- **建议方向**（一个修复可同时覆盖三条）：
  1. 给刷新请求加**与租约 TTL 绑定的客户端超时**：`AuthTransport.refresh(csrf, signal?)` 已经支持传入 signal（`session.ts:19`、`web/src/api/auth.ts:17`），在降级路径传入 ≤ 租约 TTL 的 `AbortSignal`，超时后按 §4.3「结果不明的网络失败」处理——清空内存令牌 + 引导重新登录，**不重放**。这样持有者永远不会活过自己的租约，(a) 与由它派生的 (c) 一并消失。
  2. 接管前复核 `usable(snapshot)`（`session.ts:120-122` 已有），对齐 Web Locks 分支 `:162` 的既有做法；写租约后回读确认自己仍是 owner（尽力而为的 CAS）。
  3. `clear()` 改为「owner 匹配才删」。
  4. 补一条「持有者刷新永不 resolve 时，同一时刻只有一次刷新在飞行」的回归用例。
- **关于「加超时是否与 §4.3 不自动重放冲突」**：不冲突。§4.3 要求的正是「结果不明 → 清空并引导重新登录、不自动重试」；超时后 abort 并清空完全符合。真正违反 §4.3 的是当前实现——在首次请求仍在飞、结果不明时，由另一个标签页**自动发起了同一枚令牌的第二次刷新**，这正是 §2.3 禁止的浏览器级等价物。
- **是缺陷还是规格窗口**：**是实现缺陷**。`spec.md:96` 的「最长 10 秒」限定的是**租约元数据**，「可被接管」是持有者已死的存活兜底，规格从未授权在持有者仍在飞时并发第二枚请求；§2.3、§3.3、§4.3、AC-10 四条可以同时满足（把持有者的请求寿命限定在租约内即可），因此不是规格自相矛盾。
- **可达性与限制**：需浏览器没有 Web Locks（Safari < 15.4、Firefox < 96、旧 webview）。`http://localhost` 与 https 都是 secure context，在规格指定的 Compose/生产形态 + 现代浏览器下 `navigator.locks` 存在，走 Web Locks 分支，本条不被触发（实测 `http://127.0.0.1` 下 `isSecureContext: true`，对照组只发 1 次刷新）。但 AC-10 明确要求该降级分支成立。18% 为本机数值；(b) 的机理与机器无关。真实浏览器下该分支未由本 change 的验收覆盖（`test-spec.md:90` 自述）。
