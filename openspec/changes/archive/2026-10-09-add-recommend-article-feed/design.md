# Design

## Context

见 [proposal.md](proposal.md)。现有匿名 latest 由 PostgreSQL 按固定有效发布时间与 ID 分页；文章搜索已有 OpenSearch 读别名、BM25、可选查询 Embedding/KNN、RRF 和 PostgreSQL 当前身份复核。反馈画像端口提供最多 500 篇样本、主题/来源证据与对候选 ID 独立检查的有效负反馈，但尚无关键词证据。搜索冻结游标只服务显式查询，其候选与分页语义不能直接作为推荐游标。Web 首页目前只有 latest。认证默认关闭；推荐路由必须一直可用。

## Goals / Non-Goals

**Goals:**

- 把候选、当前公开事实、本人画像与 latest 补位组成一个有界、可测试的读取用例。
- 在独立游标中固定推荐顺序与身份，允许每页重新检查下架和新增负反馈。
- 让搜索故障只改变推荐模式，不改变 latest、搜索的既有故障语义或核心 readiness。

**Non-Goals:**

- Redis 文章/Feed/推荐缓存、持久化推荐结果、在线学习、曝光计数或基于 IP 的匿名画像。
- 改造现有搜索端点的排序、游标或故障契约；向领域层引入 OpenSearch/HTTP 类型。

## Decisions

### 1. 推荐应用服务独立编排

在 `application/recommendation` 增加推荐用例和端口，复用 `articlefeedback.ProfileService`、PostgreSQL 公开读取及搜索基础设施，但不调用 `articlesearch.Search` HTTP 用例。推荐有自己的候选请求、排序、游标与模式；OpenSearch 适配器实现有界候选端口，首查最多取 100 个词项/主题候选与 100 个语义候选。这样可使用现有 RRF 常数 60 和向量身份规则，同时避免把必填 `q` 的搜索契约改成无查询推荐。备选方案是构造合成 `q` 调用搜索端点；它会错误继承搜索的 `503` 和搜索游标语义。

### 2. 画像与候选规则

扩展反馈样本的当前修订 AI 关键词读取，沿用阅读按日去重、收藏唯一、负反馈 180 天、每篇正向阅读最多 3 日、最多 500 篇样本和每个词项权重 `[-20,20]` 的界限。有效文章级排除仍对当前候选独立批量查询，不受 500 篇样本截断。仅从正权重关键词/主题各取前 3 个，按权重倒序、文本正序形成固定查询计划；无正向证据走冷启动。检索端以这些词项和主题建立一个 BM25 查询，语义启用且兼容时把同一规范化短文本生成一次查询向量。两路候选按当前公开事实与向量身份校验后重新编号并 RRF 融合；BM25 为空不阻止 KNN 或 latest，KNN 为空不阻止 BM25。查询模型与 KNN 沿用搜索的独立超时上限，总推荐首查采用单独配置的有限预算。备选方案是从全部历史文章生成自由文本画像；它难以限界且难以解释。

### 3. 排序版本 1 和来源打散

先计算基础分：`60 × RRF + 0.6 × 主题正权重/20 + 0.4 × 关键词正权重/20 + 0.15 × 来源正权重/20 + 0.3 × exp(-文章年龄天数/14) - 0.25 × 主题负权重绝对值/20 - 0.2 × 关键词负权重绝对值/20 - 0.2 × 来源负权重绝对值/20`。年龄按首查 UTC 时间与固定有效发布时间计算，并夹在零与上限内；无向量、无 AI 标签或无 Source 的项只缺对应贡献，不被排除。按基础分选下一篇时，若其 RSS Source 与上一篇相同，临时减 `0.35`；每一步以临时分、固定有效发布时间、ID 构成全序，冻结选出的完整候选序列。相同来源惩罚只影响相邻两篇，不能消灭候选资格；文章级负反馈始终先于打分排除。备选方案是对整个来源设置硬配额；在来源少时会产生无谓空页。

### 4. 冷启动和 latest 补位

匿名或无有效正向词项/主题画像直接使用 PostgreSQL latest 键集顺序；登录用户仍批量排除其当前有效负反馈。个性化候选去重、过滤、排序后不足一页时，从 latest 的头部按键集顺序补位，跳过冻结候选 ID 与当前排除 ID。以后续页继续 latest 键集，不跨页重启扫描。OpenSearch 整体不可用时直接从 latest 起步并返回 `latest_fallback`；语义单路失败只减少语义贡献。候选不足返回 `personalized` 与 `degraded=true`；一页候选用尽但暂未需要补位时，在切入补位的页面设置 `degraded=true`。备选方案是候选耗尽后结束分页；它会让明明有公开文章的 Feed 提前变空。

### 5. 推荐游标与可见性

使用独立于搜索游标的 v1 认证加密格式，记录排序版本、匿名/用户身份绑定摘要、首查模式和降级标志、绝对到期时间、最多 200 个已排序候选 ID（语义候选另含可验证向量身份）、推荐消费位置、latest 键集位置与补位阶段。AAD 与派生密钥用途限定为 recommendation，游标不得与搜索/latest 互认；`limit` 可变但不改变冻结次序。首查后不重复搜索、Embedding 或排序。每页批量从 PostgreSQL 重读当前公开 ArticleItem，丢弃下架/删除和失效语义身份；登录用户对本页及补位扫描范围重新读取有效文章级排除。被过滤项推进消费位置，继续有界扫描，避免重复和死循环。新文章不进入已有候选数组，latest 键集按现有 latest 的非快照语义避免正常插入导致重复；游标到期或进程密钥变动返回 `INVALID_CURSOR`，Web 从第一页重试。游标只保存受限事实，不包含原始画像、向量或正文。生产使用独立 `VELIS_RECOMMEND_CURSOR_KEY`；开发环境可生成进程级随机密钥，启动日志提示跨重启游标失效。备选方案是 Redis 服务端会话；本次明确不引入缓存，也无需维护推荐状态表。

### 6. HTTP、Web 与观测

公开路由使用可选认证：无凭证按匿名处理，有凭证则必须验证，错误凭证返回现有认证错误；用户 ID 只来自服务端身份上下文。成功页以固定 `mode`、`degraded` 和每篇一个枚举 `recommendation_reason` 表达推荐依据，原因按最强实际贡献择一；latest 补位不得标记为偏好匹配。Web 默认 latest，切换 Feed 或身份变更时取消请求并清理列表、游标与反馈状态，推荐降级显示轻量提示。统计模式、固定枚举降级原因、召回/过滤/补位数、来源分布桶与耗时；不记录画像、向量、游标或正文。备选方案是返回原始分数与偏好词；它增加泄露面且对用户解释帮助有限。

## Risks / Trade-offs

- **候选上限 200 篇** → 深页进入 latest 补位；OpenAPI 明确该界限，观测补位量和来源分布。
- **游标携带候选数组可能偏长** → 对候选数与编码长度设硬上限；超限按受控降级或缩小候选预算处理，绝不发出无法解码的游标。
- **画像与候选之间的状态变化** → 首查排序冻结，每页仍复核当前公开事实和有效负反馈；正向反馈变化只在新首查生效。
- **进程级开发密钥在重启后失效** → 生产配置共享独立密钥；Web 对 `INVALID_CURSOR` 提供从第一页恢复。
- **PostgreSQL 读取失败无法安全降级** → 返回依赖错误，不使用索引投影直出或忽略负反馈。

## Migration Plan

不新增业务事实表或改写既有迁移。先扩展画像与推荐读取端口、再装配 HTTP 和 Web；部署时为生产 API 实例配置相同的推荐游标密钥，确保旧实例在滚动期间能验证新游标。OpenAPI、示例配置、README 与 Roadmap 随实现更新。回滚到旧版本时新接口不再可用，既有 latest、搜索、反馈和文章事实保持不变；新推荐游标自然失效，无需数据回滚。
