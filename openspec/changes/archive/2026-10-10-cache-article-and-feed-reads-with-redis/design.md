# Design

## Context

动机与范围见 [proposal.md](proposal.md)，行为以四份 delta specs 为准。当前相关实现：

- `application/article.Service.List` 调用 `ArticleRepository.ListPublished(limit+1)`，使用 v2 `(SortAt,ArticleID)` 游标；详情直接调用 `GetPublished`。
- PostgreSQL 的 `ListPublishedByIDs` 和 `ListPublishedWithIdentity` 在完整联表 SQL 中同时读取当前事实与卡片，后者还提供 revision/generation/embedding/profile 身份；搜索和推荐依赖这些端口进行批量复核。
- 推荐 `Service.get/plan/page` 区分新首查和续页，首查聚合当前画像、召回、融合、硬排除、排序，续页通过客户端加密游标复核当前事实与本人排除。画像为空候选读取时并不提供全部文章级排除集。
- `ports.TxManager` 和 PostgreSQL `WithinTransaction` 支持上下文中的嵌套事务复用。RSS `source.execute` 的完成事务包含 `article.Ingest`；用户和管理员文章命令的事务由幂等服务持有，不能把内层返回成功当作已提交。
- Redis 当前只有 `infrastructure/cache/redis/doc.go`；Compose 有 Redis 服务，但尚无客户端、业务配置、缓存指标或真实测试入口。

## Goals / Non-Goals

**Goals:**

- 保留当前公开修订、增强选择、语义身份和本人负反馈的正确性；缓存只减少重复载荷读取和推荐计算。
- 将列表候选发现的新鲜度和卡片内容的新鲜度分开；默认 latest 候选绝对寿命 5 秒，当前卡片仍按数据库事实装配。
- 以有界批次、短超时和同步最佳努力回填实现清空后自行恢复，不依赖额外常驻补缓存任务。
- 保持 Application 定义读取/缓存/提交后动作端口，Infrastructure 实现 PostgreSQL、Redis 和 SDK，bootstrap 装配；不将键或 SDK 类型放进 Domain。

**Non-Goals:**

- 首版不做缓存高可用集群、跨地域、全局版本槽位、分布式锁、画像缓存、正文缓存、搜索召回缓存或 Redis 分页会话。
- 不为缓存新增可靠 MQ 消费链，不改变业务 Outbox 的原子性；失效失败通过 TTL 收敛。
- 不设置吞吐、命中率或延迟改善比例门槛；只保留固定负载下可解释的前后数据。

## Decisions

### 1. 统一卡片读取端口，缓存不可变片段并实时装配动态字段

新增 `application/articleread` 一类共享读取编排模块，提供按 ID 装配卡片和当前语义身份的端口，供 latest、BM25/混合搜索、推荐计划与推荐分页复用。现有写 Repository 保持 PostgreSQL 实现，不用同时覆盖读写的缓存 Repository 装饰器。

卡片分成两部分：

- 缓存片段：不可变 revision 的标题、excerpt、源作者名，以及当前 generation 对应的摘要、关键词、主题、生成时间和来源标记。片段绑定 article/revision/generation；无 generation 使用显式空选择标识。
- 当前事实：公开状态、revision/generation 身份、有效发布时间、来源/原文 URL、作者 ID/昵称、Source 摘要，以及当前有效 embedding/profile 身份。轻量 SQL 仍对 generation/embedding 做原有归属校验，只不读取大文本和数组载荷。

按当前事实选择缓存片段并组合现有 `ListItem`，向量身份始终来自当前事实。作者昵称或 Source 小字段不进入长寿命片段，避免引入跨对象失效机制。缓存值包含格式版本、身份、生成/绝对到期时间及载荷校验摘要；限制大小、字段、ID、来源类型和增强来源枚举。错误只降为未命中，不把缓存读取异常转换成公开文章不存在。

选择片段而非整个最终 DTO，是因为当前卡片中有跨聚合动态字段；仅用 article/revision/generation 键不足以保证昵称和排序字段最新。详情继续直接走现有 PostgreSQL 查询。

### 2. 每批事实与回源片段使用同一短只读快照

新增应用层只读快照端口，PostgreSQL 以 `READ ONLY REPEATABLE READ` 实现，并复用现有 `querier` 上下文机制。每批流程为：批量读取事实 -> 有界批量读缓存 -> 批量加载缺失片段及其实际身份 -> 结束只读快照 -> 最佳努力批量回填。所有卡片数据库查询必须使用该快照连接。

缓存片段的回源查询携带实际 article/revision/generation，写键由实际身份构造；严禁分别读取旧载荷和新版本后拼成一个回填值。并发写在该批快照之前提交时，看到新事实；在快照之后提交时，该请求允许看到完整旧视图，与并发数据库读取的语义一致。下架过滤以每批当前事实读取为线性化点，不承诺撤回已发送响应或修改客户端旧页面。

只读快照不包裹 OpenSearch/Embedding 调用。卡片命中也必须成功读取 PostgreSQL；现有错误映射保留。写事务中的读取不得填充公开缓存或把未提交片段传播出去。

使用同一快照避免拆分 SQL 后出现内容与身份错配。备选逐次最终版本重读需要冲突重试和额外数据库轮次，首版采用更易验证的批次快照。

### 3. 三类键独立版本与绝对 TTL

键由 Redis 适配器生成，应用端口接收有类型身份和请求描述。示意：

| 对象 | 键身份 | 默认 TTL | 初始上限 |
| --- | --- | --- | --- |
| 卡片片段 | `<namespace>:card:v1:<article>:<revision>:<generation-or-none>` | 5m | 单值 64KiB，批次最多 100 项 |
| latest ID 页 | `<namespace>:latest:v1:<limit>:<normalized-position-hash>` | 5s | 每页最多 limit+1，即 51 项 |
| 推荐首查计划 | `<namespace>:recommend:v1:<authenticated-user>:<profile-hash>:<config-hash>` | 30s | 原始候选与排序项各最多 200，单值 128KiB |

摘要仅用于稳定编码/校验，不替代认证；键不得写日志或用作指标标签。前缀区分项目和环境，测试另加每次运行的随机命名空间。

封装 `created_at/expires_at`，卡片以原始片段读取时间、ID 页以候选查询开始时间、计划以首查计划开始时间计算到期。回填用剩余寿命，已经过期直接跳过；读命中不刷新 TTL。这样并发失效后迟到的旧回填也无法重新获得完整寿命。默认 latest 的 5 秒是正常依赖下的候选新鲜度目标，不能被解释为页面自动更新或故障下硬 SLA。

Redis 使用成熟 Go 客户端，固定依赖版本，实现批量 GET/MGET、带剩余 TTL 的 pipeline SET 和有界 DEL。首版按单实例能力实现。自动命令重试关闭，不使用 key 扫描清理生产缓存；类型错误、非法 JSON、校验摘要/身份不符和超限都按未命中处理。过期键由 Redis 清理。

### 4. latest 候选页有界补页，首页提交后尽力失效

`article.Service.List` 校验参数并解码现有 v2 游标后，通过 latest 读取端口获得 `limit+1` 个 `(id,sort_at)` 候选和候选耗尽标识；未命中时使用当前 `articles_latest_idx` 对应的轻量键集 SQL。缓存不保存最终已过滤响应或卡片。

装配时按候选顺序恢复结果，丢弃不可见文章。候选的当前 sort_at 若与缓存位置不一致，整批按原请求位置重新读取；不能混用两个排序位置。页面被过滤时从最后已检查候选位置继续读候选批，最多检查 500 个候选。收集 `limit+1` 个有效结果形成 lookahead；有效 lookahead 不被消费，续页从已返回/已检查位置继续。若达到扫描上限仍未耗尽，则返回可推进的游标，必要时允许短页或空页，但不能重复、跳过有效 lookahead 或死循环。参数合法但空池正常缓存空候选页，寿命仍为 5 秒。

影响公开列表的发布、恢复、下架/删除及 RSS 公开条目更新，在最外层事务提交后执行首页失效。首页用固定位置标识，枚举合法 limit 1..50 的键作一次有界 pipeline/DEL，避免维护键索引或扫描。续页键依靠 5 秒绝对寿命收敛。

在技术事务端口增加提交后动作登记：嵌套用例登记到同一个外层事务，Commit 成功后去重执行一次首页失效；回滚、提交失败丢弃动作。独立写入也必须先确认最外层提交。失效的错误被吞为缓存指标，不改变原命令的成功、失败或幂等重放结果；回调使用独立短预算且受进程生命周期管理，不创建脱离管理的后台 goroutine。

直接失效是降低常见延迟的优化，绝对 TTL 才是失效失败和回填竞态下的收敛手段。备选 PostgreSQL 全局列表版本会增加写入协调与持久元数据，当前新鲜度契约不需要。

### 5. 推荐计划绑定当前画像，并检查原候选排除签名

新首查仍调用现有 Profile 端口。指纹覆盖规范化排序后的 keyword/topic/source 的所有排序证据，包括 Weight、PositiveWeight、NegativeWeight 和样本量；配置指纹覆盖排序版本、候选数、有效语义开关、provider/model/profile/维度、输入版本与影响计划的预算参数。用户 ID 来自服务端认证，登录用户键不能退为匿名、设备、IP 或画像哈希分区。

缓存位置在现有 `plan` 的有界召回/事实校验/排序之后、`page` 之前。缓存结构保存：

- 最多 200 个排序 FrozenItem、实际语义降级标志/原因、配置/身份标识和绝对到期时间；不保存游标、offset、latest 水位或画像。
- **硬排除之前** BM25/KNN 并集的原候选 ID（最多 200）及当时本人有效排除集的确定性签名。排序项必须是原候选 ID 的子集。

命中后对原候选 ID 批量读取本人当前 Exclusions；签名变化则当作 miss，按当前事实重新生成计划。不能只比较已排序项，因为这些项已经丢掉原先被排除的文章；也不能仅依赖画像指纹，因为无标签文章的负反馈撤销可能不改变画像。此方案不改变现有 RankV1 的“先硬排除再来源打散”语义，也无需新增用户版本表。

未变化的命中计划仍走现有 `page` 当前可见性/语义身份/有效负反馈复核，避免命中检查与返回之间的并发反馈被忽略。每次新首查建立自己的 StartedAt、ExpiresAt、初始 offset 和 latest 水位；不直接复用某次 HTTP 响应或加密游标。已有游标不读取计划缓存、不重新聚合画像或召回。

只缓存成功生成的有界候选计划，包括实际存在的 BM25 语义降级标志；不缓存 `latest_fallback`，不把 PostgreSQL/画像失败或召回失败写成空成功计划。匿名和登录无正向画像沿现有冷启动路径，首版不增加冷启动计划缓存。推荐 latest 补位保留其 userID、skip、StartedAt 约束，通过专用轻量数据库候选查询和共享卡片装配优化，不直接复用 `/articles` 的匿名 ID 页。

### 6. 配置、装配和故障预算

新增 `cache` 配置，优先级保持默认 < YAML < 环境变量；启用时校验静态配置，但 Redis 运行时不可达不能阻止 API/Worker 启动。SDK、pool 和 close 位于 bootstrap。API 的卡片/latest/推荐共享一个客户端，Worker 只装配提交后失效；启动与 readiness 不强依赖 Redis。

| 配置 | 默认/校验 |
| --- | --- |
| enabled | false；Compose 开发示例显式开启，可用环境变量关闭 |
| redis.address / database / tls | 开启时显式地址；库号非负；TLS 可选，凭据只从环境变量读取 |
| namespace | `velis:<environment>`；非空、有限长度且限制字符；API/Worker 相同 |
| card_ttl / latest_ttl / recommend_ttl | 5m / 5s / 30s；分别允许 1s..1h、1s..5s、1s..30s |
| operation_timeout / request_budget | 50ms / 100ms；分别 5ms..100ms、10ms..200ms，单次不大于总预算 |
| pool_size / batch_size | 10 / 100；有界整数，批次最大 100，连接池最大 100 |

总预算累计实际 Redis 调用耗时，跨首查计划、卡片、latest 补页和回填共享；每次调用取 operation_timeout、剩余缓存预算与父 deadline 的最小值。原有 PostgreSQL/OpenSearch/推荐总 deadline 保留。首次 Redis 传输失败或预算耗尽后该请求后续缓存操作直接绕过，避免多个批次重复承受超时；回填是剩余预算内的最佳努力。Redis 错误不使用请求取消错误掩盖真正父 context 取消，也不吞掉 PostgreSQL 错误。

首版不做进程级熔断；连续请求中缓存故障仍可能带来有界额外等待，这是明确接受的初期代价。恢复后新请求自动尝试并逐步回填。

### 7. 可观测性与验收负载

新增固定 `object=card|latest|recommend`、`operation=get|set|invalidate`、受控 result/reason 指标，分别记录条目命中/未命中、批次回源、损坏、故障绕过、失效/回填失败和调用耗时。定义条目计数与操作计数，避免将 MGET 部分命中混为整次请求命中。request ID 关联日志，不记录缓存键、用户 ID、画像、游标或内容。Redis 故障不单独设置推荐 degraded；原有搜索/语义/候选不足原因继续生效。

实施前记录关闭缓存的基线；同一固定语料、用户信号、并发和请求序列比较关闭、冷、热、损坏、故障、恢复状态。建议小型负载为 1000 篇文章、两名不同偏好用户、每页 20、并发 5；覆盖 latest 首页/续页、BM25 与开启混合时的搜索装配、recommend 首查/续页。报告总延迟及 P50/P95、数据库调用/读取载荷、OpenSearch/Embedding 次数、缓存命中与回源。语义通道使用确定性桩或明确的测试配置；不使用真实收费模型作为默认验收。没有改善也必须如实记录，不能仅报告命中率。

新增真实 Redis 测试入口及 harness。清空缓存通过删除测试运行拥有的随机前缀键模拟，禁止 FLUSHALL 或清理共享 Redis 库。断连/慢响应优先使用测试进程拥有的代理或客户端故障注入，恢复后连回专用测试实例；不停止共享服务。PG 沿现有 `_test` 双重保护，OpenSearch 使用测试独占索引。缺少必需测试变量时专用验收入口明确失败，单测 skip 不算真实验收通过。

## Risks / Trade-offs

- [ID 候选短暂滞后] -> OpenAPI 和文档明确 latest 候选窗口；详情和实际返回卡片仍使用当前事实，主动失效降低通常延迟。
- [旧回填发生在失效之后] -> TTL 从原始读取时间计算且不续期；卡片用不可变版本键，旧数据不能覆盖新版本。
- [拆分读取产生混合版本] -> 每批短只读快照和实际身份回填；并发测试证明内容/身份不会错配。
- [负反馈撤销没有改变画像] -> 缓存保留硬排除前的原候选 ID，命中检查排除签名，不新增用户版本事实。
- [过滤后页面不足或空转] -> 有界补页、正确区分 lookahead 与已消费位置、扫描上限游标推进及回归测试。
- [Redis 中断时回源增加数据库压力] -> 保留批量上限、连接池和请求 deadline；首版接受有界回源，后续基于测量考虑合并同键请求或熔断。
- [只读快照占用连接] -> 单批最多 100 卡片、Redis 单次 50ms/总预算 100ms，快照不跨搜索或模型调用；报告冷缓存与故障的连接代价。
- [推荐排序与候选元数据滞后] -> 30 秒绝对计划窗口，返回卡片仍当前；语义身份失效过滤，画像/排除变化新首查重算，已有游标维持现有冻结行为。

## Migration Plan

1. 无数据库迁移；先记录关闭缓存基线，再完成端口、配置、批量读取、提交后失效及 Redis 适配器。
2. 默认关闭，通过开发 Compose 和测试环境显式开启，完成真实依赖故障/清空/恢复验收和原有搜索推荐回归。
3. 更新 OpenAPI、示例配置、README、Roadmap 和测试说明，只描述有实现证据的状态；本 change 的实施不包含生产部署。
4. 回滚先关闭 cache.enabled，即恢复原事实源读取；旧版本键自然到期。保留客户端现有游标格式，既有有效游标仍可继续；不删除业务数据或更改历史迁移。
5. 后续改变缓存对象格式时独立推进对象键版本，旧键不兼容则 miss，避免把缓存格式升级与公开游标升级绑定。
